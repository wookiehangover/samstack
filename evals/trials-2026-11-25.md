# With-skill and no-skill trials

Date: 2026-11-25 UTC. Skill revision: commit `f269d5e` (samstack 0.3.0 text). Node `v24.22.1`.

## Method

- Seven fixtures, one per skill, each with one planted problem. The prompts are in the [evaluation guide](../EVALUATION.md) and do not state the answer.
- Fourteen separate agent sessions: each prompt once with “First read `skills/<name>/SKILL.md` and apply it”, once without. Every session reported the model `gpt-6.2-sol` through Codex; the serving model was not independently verified.
- Each agent was told to work only inside its fixture directory, to put scratch files in its private temporary directory, and to change nothing in the repository.
- The [answer key](answer-key.md) was written before the first trial and kept outside the repository until all fourteen had finished.
- A separate grader session (session-reported model `fable` through Claude Code) scored the fourteen final answers against the key. The answers were given letters in shuffled order with no mention of skills, and the grader was told to score each criterion 1 or 0 from the text alone.

## Checks on the trials

- The tool calls of all fourteen sessions were read afterwards, including shell commands that were long enough to be cut off in the first view. No session opened a path outside its fixture, apart from the one skill file in the with-skill arm. No no-skill session opened a skill file. All seven with-skill sessions read their skill.
- After the trials the working tree was clean, `HEAD` was unchanged, the skill files matched their recorded SHA-256 digests, and the built history repository was unchanged.

## What this shows

- **Every no-skill answer found the planted problem.** The first criterion of each fixture is the core finding, and all fourteen answers met it. The fixtures did not catch this model out.
- **The with-skill answers were more complete and easier to check.** The points the no-skill answers lost were for not showing the commands they ran (blast-radius, interrogate), not saying what was still unknown (why), not naming a practical constraint (how), not naming the assumption the failed fixes shared (engineering-principles), and giving one design with no caller example or alternative (architect).
- **architect shows the only large difference**: 2 of 5 without the skill, 5 of 5 with it.
- **interrogate was level**, with different misses. The with-skill answer listed a route-table hardening item among its verified findings.
- **benchmark-checklist was level** at 5 of 5.

## Limits

- One run per arm. A one-point difference on one run can be chance.
- One model. A weaker or different model may behave differently in either direction.
- The author of the answer key also edited the skills. Criteria 2 to 5 partly reward things the skills ask for, such as showing commands or sketching two designs, so the key leans toward the with-skill arm by construction.
- The grader was not told which answers used a skill but could guess from their style.
- The fixtures are small and synthetic. The agents ran in parallel on one machine, inside Intent task sessions.
- Not tested: whether a client loads a skill from its description alone, and the negative trials in the evaluation guide.

### interrogate, no skill (trial 07)

````markdown
**Block the merge. Frequent requests can stop a client’s bucket from refilling.** At `src/limiter.mjs:16–18`, each call rounds the earned tokens down and advances the timestamp, even when the request is denied. At the production rate of one token per second, each 500 ms retry earns half a token and discards it. I verified that two writes drain the 10-token bucket, then all 130 reads spaced 500 ms apart get 429. A read after a full second of silence gets 200. The limiter should carry fractional refill credit across calls, including denied calls.

Two other edge cases are visible in the implementation.

- `src/limiter.mjs:2,16–18` uses wall-clock time. If the clock moves backward, the refill calculation subtracts tokens. Use a monotonic clock for elapsed time.
- `src/routes.mjs:3–6` looks up costs on a plain object. An unknown kind that matches an inherited property, such as `toString`, gets that property instead of the default cost of 1. Restrict the lookup to the table’s own entries.

`node test/limiter.test.mjs` passes. Its refill checks advance the clock by whole seconds and miss the frequent-retry failure. Add a fake-clock regression that drains the bucket, expects 429 at 500 ms, and expects 200 at 1,000 ms despite the intervening denial.
````

### architect, no skill (trial 14)

````markdown
Expose `cancel(jobId)` on the object returned by `start()`. The coordinator owns the decision and returns `cancelled` for a queued job, `cancelling` for a job whose worker is still stopping, `already_finished` for a completed or dead job, and `not_found` for an unknown ID. Repeated calls return the current outcome. Keep terminal outcomes for the lifetime of this in-memory fixture so callers can poll with the same call and successful acknowledgements can still remove jobs from the active map.

**Queue and worker protocol**

- Cancel a ready job synchronously in the coordinator so the next claim skips it. For a leased job, change its state to `cancelling` before sending a cancel message to its worker. A job in that state is ineligible for claims and retries.
- Give every claim a unique attempt token. Include it in heartbeats, acknowledgements, failures, cancellation messages, and stop confirmations. The coordinator validates the token, the sending child process, and the job state on every update. Worker IDs such as `w0` are reused when a child restarts.
- Give each attempt an `AbortController` and pass its signal to the handler. Make the fixture’s sleeps abortable and check the signal immediately before the email handler appends to the log. Install the controller when processing the claim reply, before invoking the handler. Send the claim reply and subsequent cancellation over the same child IPC channel in order.
- Report that the attempt has stopped after the handler and its cleanup have finished, with the heartbeat timer cleared. An ordinary completion or failure report received while the job is `cancelling` can serve as stop confirmation if it carries that same guarantee. It then finalizes cancellation without recording success or scheduling a retry. If the worker fails to stop within a short grace period, terminate that child, escalate to a force kill if needed, and finalize only when it exits. Each worker runs one job at a time.

**Races and recovery**

- The first transition processed by the coordinator wins. If an acknowledgement commits first, cancellation returns `already_finished`. If cancellation wins, a late acknowledgement or failure can confirm that execution stopped, but cannot overwrite the outcome. An external effect may already have happened before the worker receives the abort, even if cancellation beats the acknowledgement. For this fixture, cancellation stops the attempt and suppresses retries. An email log entry already written stays written.
- Change the reaper to retire a worker with an expired lease and wait for that child to exit before making its job claimable again. Keep the job associated with that attempt while the worker is stopping so cancellation can still win during that interval. This closes the window in which expiry could start a second copy while the first copy is still running.
- Route child exit through attempt-aware recovery before respawning the worker. Finalize a cancelling job and requeue an uncancelled attempt under the existing attempt limit. The current exit handler only respawns the child, even though `retryJob` exists and the README describes immediate crash retry.

Test the queue transitions with the fixture’s fake clock. Add forked-worker tests that synchronize on handler start and deliberately control when it may perform the log write. Cover queued cancellation, running abort before the write, repeated cancellation, both acknowledgement orderings, worker crash and lease expiry during cancellation, and a worker that ignores abort. Verify that cancelled jobs never run again, stale messages cannot affect a new attempt, and the worker pool handles subsequent jobs.
````

### architect, with skill (trial 06)

````markdown

```js
const jobs = start()
const id = jobs.queue.enqueue({ type: 'email', to: 'a@example.test' })

jobs.cancel(id) // { status: 'cancelled' }, whether ready or running
jobs.cancel(id) // { status: 'already-cancelled' }
```

If completion already won, the result is `{ status: 'inactive' }`. Unknown IDs and dead jobs also return `inactive`, preserving the current behavior of deleting completed records without adding completion history. A `cancelled` result guarantees the queue will never claim or retry that ID again. It means the stop request has been accepted. A running handler can take time to observe it, and side effects already performed remain in effect.

### Queue and worker responsibilities

Today, callers enqueue through the coordinator's exposed `queue`. A forked worker claims one job at a time over IPC, sends heartbeats during execution, and then acknowledges success or reports failure. Failure and lease expiry return work to `ready`. The README describes immediate crash retry, but the exit handler currently only respawns the child. The exported `retryJob` helper is unwired and scans by worker ID.

- **Queue.** Make cancellation a terminal transition from `ready` or `leased`. Clear ownership and keep a minimal cancellation record for the coordinator's lifetime so repeat calls have a stable answer. Give every claim a unique lease token and require it on heartbeat, acknowledgement, failure, and crash release. Those operations must match the current leased attempt. Apply the same check after a worker ID is reused or a job is reclaimed. The reaper only releases leased jobs. With synchronous queue transitions, acknowledgement first yields `inactive` on cancel, and cancellation first makes a late acknowledgement or failure harmless.
- **Coordinator.** Track the job and lease token each child is executing until it reports settlement or exits. Keep this tracking separate from the queue lease so an expired attempt that is still unwinding can receive cancellation too. After recording cancellation, send an unsolicited abort message carrying the token to every tracked child executing that job. Route exit-triggered retry through the queue's token-checked release operation and wire it into the actual exit handler. A cancel, an expired lease, or a newer claim can all make an old release a no-op.
- **Worker.** Create the attempt's controller when processing the claim reply, before starting the handler, and route abort messages separately from RPC replies. Abort only the matching attempt. Also abort when a heartbeat reports lease loss. Clear heartbeat and execution state when the handler settles. Report settlement even if the lease is already gone so the coordinator can retire its execution record. Pass `{ signal }` as a third handler argument, keeping the existing payload and worker ID arguments. Both built-in handlers can use abortable sleeps, and the email handler should check the signal immediately before appending to the log. Document the signal contract for custom workers supplied through `workerPath`.

### Alternative and decision

Compare the designs on how quickly execution stops, whether the job can be retried by mistake, and what changes handlers need.

- **Cooperative abort**, as above, lets a handler clean up and lets the child continue serving jobs. Cancellation reaches it as soon as it can process IPC. A handler that ignores the signal or blocks the event loop can keep running.
- **Terminate and replace the child.** Record the same terminal queue state first, then terminate each matching child and use the existing respawn path. One job per child makes this a viable design with no handler API changes. It can stop a blocked handler with forced termination, at the cost of interrupting cleanup and restarting the process. It still needs attempt tracking and guarded crash release. Work already sent to another process or service can outlive the child.

Use cooperative abort for the fixture. Both built-in handlers spend their wait in an abortable timer, and the email handler has a single visible side-effect boundary. Confirm whether callers need a bounded time to stop custom handlers. If they do, use a grace period followed by child termination and expose a separate way to wait for worker exit. The synchronous cancellation result should keep its queue-level meaning.

The existing queue test passes. For implementation, add deterministic checks for ready and repeated cancellation, acknowledgement winning and losing the race, and stale messages after lease expiry or worker replacement. Add a forked-worker test that waits for the email handler to start, cancels during its sleep, and verifies that it produces no log entry, is never retried, and leaves the worker able to run the next job.
````
